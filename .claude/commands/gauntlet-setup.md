---
description: Set up Gauntlet's policy with me, one decision at a time
---
Help me set up Gauntlet's policy for this repository. Gauntlet checks AI-written changes before they're merged; the policy in `.gauntlet/policy.gx` decides what every change must pass, including yours.

1. Read `.gauntlet/policy.gx`, the draft `gauntlet init` wrote. If it doesn't exist, tell me to run `gauntlet init` and stop.
2. Call Gauntlet's `get_grammar` and `get_examples` tools so you only propose what the policy language supports.
3. Read enough of the codebase to know where these live: money and payments; authentication, permissions and secrets; personal data; contracts other systems depend on (APIs, schemas, events, generated clients); data stores and migrations. Also note the layers (modules or packages, and what imports what) and the test layout.
4. Find what the project already has set up, from its build files, tool configuration, CI workflows and any CLAUDE.md or contributing notes: the build tool, the test frameworks, the coverage tool and any minimum it already enforces, the linter and its configuration, mutation testing, and what CI runs. Start by telling me what you found, in plain words and with specifics, for example: "You build with Gradle and test with JUnit 5. Kover already requires 80% line coverage, detekt runs with your config, and CI runs the tests on every pull request. There's no mutation testing." Build on what's there: where the project already enforces something, recommend Gauntlet matches it rather than picking a new number ("Kover already requires 80%, so I recommend an 80% floor for new code"), and say when Gauntlet would add something the project doesn't do yet. Some tools need no configuration file for Gauntlet: StrykerJS runs with the project's own test runner (Stryker's command runner for `bun test`), so having `@stryker-mutator/core` installed is enough for the mutation gate. Don't tell me a check can't run for lack of a config file; Gauntlet's setup hints and its `check` tool say exactly what's missing. If part of the project uses a language or build tool Gauntlet doesn't support (Maven, Mill, Scala CLI, Bazel, .NET, Ruby, PHP, Swift, Elixir and so on), say so plainly: that part won't be checked. Tell me I can ask for it at https://github.com/matthewjones372/gauntlet/issues/new, or add it myself by following https://github.com/matthewjones372/gauntlet/blob/main/docs/development.md#adding-a-language-pack.
5. Go through the decisions below **one at a time**. Make it easy to follow: start each with a short heading that says where we are, like "**Decision 2 of 6 · Zones**", keep each message short, and when a decision is settled, say so in one line starting with ✅. For each one, say what you found (with file paths), what you recommend and why, and what it will mean day to day (for example "changes here will need your review" or "every change must keep this passing"). Then ask me, with your recommendation first and a way to skip. Use the AskUserQuestion tool if you have it. Never ask about several decisions at once.
   - **Owner**: who approves sensitive changes and edits to the policy. Ask for my GitHub username or team (written like @my-username or @my-org/my-team).
   - **Zones**: a zone marks code where a change needs the owner's review, and can switch on stricter rules there. Go through the draft's zones first, then any areas you found that folder names missed. Suggest the language's rules that fit (for example no floating-point money).
   - **Layers**: which parts must never import which (for example the domain never imports the web layer).
   - **Tests and coverage**: how much of the new and changed code must be tested (match what the project already enforces; otherwise 80% recommended, 70%, or only "never less than today"), and a mutation score if a mutation tool is set up.
   - **Mutation testing** (only if a mutation tool is set up, or I choose to set one up): most people haven't met it, so explain it before asking. In plain words: it makes small deliberate bugs in the code (turning a `>` into `>=`, say) and runs the tests against each one; a bug no test catches shows a test that runs the code but doesn't really check it. Then warn plainly that it runs the tests once for every bug it makes, so it's by far the slowest check: minutes where the tests take seconds, and far longer across a whole project, on every check and in CI. Recommend running it only on the lines a change touches (`mutation >= 60% on changed`), and only in the zones that matter if the project is big (`... on changed in zone payments`). Offer leaving it out as a real choice, and say what each choice means for how long a check takes.
   - **Formatting**: a formatter ends arguments about layout and keeps diffs small. Recommend the language's standard one, checked by Gauntlet's lint check: Kotlin ktlint (as detekt's `detekt-rules-ktlint-wrapper`, fixed with `detekt --auto-correct`), Java google-java-format (through Spotless), Scala scalafmt, TypeScript Prettier or Biome, Python ruff format, Go gofmt, Rust rustfmt, Clojure cljfmt. A new project starts with it on; in an existing one, format the whole project in one commit of its own first, never mixed with other changes, and only if I agree.
   - **Lint and compiler warnings**: say what's configured now (for example "detekt with your config; compiler warnings aren't errors"), then recommend, in plain words with what each catches. A new project, or one with no warnings today, starts strict: compiler warnings fail the build, and the recommended rules are on. Kotlin: detekt on its default rules (`buildUponDefaultConfig = true`) and `allWarningsAsErrors`. Java: Error Prone with NullAway, and `-Xlint:all -Werror`. Scala: scalafix with RemoveUnused, OrganizeImports, DisableSyntax (no null, var, throw or return) and ExplicitResultTypes on public members, and sbt-tpolecat for strict compiler flags (`-Werror`, unused warnings). TypeScript: `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and typescript-eslint's strict-type-checked rules (or Biome's recommended set). Python: ruff with E, F, I, B, UP, SIM and S, and mypy `--strict` or pyright strict. Go: golangci-lint with govet, staticcheck, errcheck, gosec, revive and ineffassign. Rust: clippy with `-D warnings`. Clojure: clj-kondo failing on warnings. In a project that already has lint findings or compiler warnings, recommend the linter with its findings recorded in the baseline (`lint ratchet`: old findings don't block, new ones do), and say that making compiler warnings errors would break the build today, so leave that until they're fixed. Build and linter configuration is protected, so these go in `gauntlet.changes.patch`.
   - **Missing tools**: for each check that can't run because its tool isn't set up (type checking, lint, coverage, mutation), ask me: set it up now, or skip it for now. For a mutation tool, first explain what mutation testing is and how much longer it makes every check (as under Mutation testing above), so slow builds don't surprise me. Give the exact command, using the project's own package manager (for example `uv add --dev mutmut` or `bun add -d @stryker-mutator/core`), and recommend setting it up when it's one dev dependency. If I say set it up, run the command, check that the tool now runs, and include the check. When setting it up means writing a protected file (a build file such as `build.sbt` or `project/plugins.sbt`, a linter or coverage config such as `.scalafix.conf`), don't write it and don't create it or its folder with a shell command: those are locked for you and will be refused. Add it instead, as a unified diff (`--- /dev/null` for a new file), to `gauntlet.changes.patch`, and include the check. `gauntlet apply` applies that patch before the policy, so it needs no separate step. If I skip it, leave the check out and tell me how to add it later.
   - **When to block**: stay in shadow mode, which only reports (recommended to start), or block failing changes now.
6. A protected file you need to change goes in `gauntlet.changes.patch`, never through a shell command. When a check blocks you on something else you aren't allowed to change (Gauntlet's, or the project's own Stop hook or gate), never just wait. Work out the cause of each failure and give the person the exact commands that fix it, one per code block, each with a one-line reason. If the same block comes back twice, stop and say so instead of trying again. Never make the policy weaker than the draft without saying so plainly ("this removes …, which makes the policy weaker") and getting my yes. Don't restate what Gauntlet already does by default: its integrity checks (new skips, weakened tests, suppressions and so on) are always on.
7. Write the whole policy to `gauntlet.proposal.gx` in the repository root, then check it with Gauntlet's `validate` tool, passing `file: "gauntlet.proposal.gx"` (not the text). Fix any problem until it's valid. You can't and mustn't edit `.gauntlet/` yourself.
8. Show me a short summary headed "This will be applied:", one plain line per change from the draft, and mark anything that loosens it. If you wrote `gauntlet.changes.patch`, add one line per protected file it changes, with why. Don't paste the whole policy.
9. Ask me whether to apply it now, with "Apply it now" first and "I'll run gauntlet apply myself" second (use AskUserQuestion if you have it). Only on my yes, run `gauntlet apply` yourself: it applies `gauntlet.changes.patch` if there is one, lists the changes again (marking anything that loosens the policy), writes and commits the policy, records the baseline and switches on Gauntlet's hooks. Then tell me in plain words what it did and what it found, without pasting its output.
10. Once it's applied, run Gauntlet's `check` tool on the project as it is. If everything passes, say so and stop. If something fails (tests, lint, coverage, a missing tool), tell me what failed in plain words, then ask: "Do you want me to try to fix these? I'll report every change I make." Use AskUserQuestion if you have it, with "Fix them" first and "Leave them for now" second.
11. If I say fix them, fix what you can: failing tests, a broken build, new findings. Leave alone findings the baseline already records (lint findings that were there before): they're grandfathered and block nothing. Never run a linter's bulk auto-fix across the project (`biome check --write`, `eslint --fix`, `ruff check --fix` and the like): it can fight the compiler and break the build. Protected files (test setup, build files, linter and coverage config) are locked for you, so an edit to one will be refused. Tests aren't: you can fix a wrong test, and the change then needs review. When a fix needs one, don't work around it and don't send me to another terminal. Write the change as a unified diff to `gauntlet.changes.patch` and ask me, in these words or close to them: "To get the first baseline passing I need to change these protected files: (each, with why). I'll only do this once, for the first baseline, and you'll need to review these changes after setup. Apply it now?" On my yes, run `gauntlet apply` yourself: it shows the diff, applies it and commits it on its own. Never weaken a test to make it pass: integrity checks still run.
12. When you're done, give me a report: every file you changed and why, with protected tests listed separately. If a Gauntlet adoption window is open (`gauntlet adopt --status` says so), close it yourself with `gauntlet adopt --close` and include its record in your report; never ask me to. 
13. Setup's commits are on the branch `gauntlet/setup` (`gauntlet apply` moved them there when it started on the default branch). Never push to the default branch: the default branch gets Gauntlet only through a pull request, where the project's own CI runs, and Gauntlet's hook refuses such a push. Ask whether to check pull requests on GitHub too, with "Add the GitHub check" first and "Not now" second (use AskUserQuestion if you have it). Explain it in one line: every pull request gets a `gauntlet` check, judged with the policy and tests from the base branch, so a pull request can't weaken them. On yes, run `gauntlet connect github --protect-only` if I want just the tamper check, or `gauntlet connect github` for the full policy (ask which, recommending the full policy), and commit what it writes on the same branch.
14. Then ask "Open a pull request for the setup?", with "Open the pull request" first and "Not now" second. On yes, push the branch (`git push -u origin gauntlet/setup`) and run `gh pr create` with a title and a body that says, in plain words, what setup changed: the policy, the baseline, the tools it set up, and each protected file it changed with why. Tell me to merge it once its checks pass, and that if a check fails, it's the project's own failure to fix first, not something to push past.
15. Once that pull request is merged (ask me; if it isn't yet, tell me to come back to you after merging), ask whether to require the check, with "Require it for everyone" first (recommended: nothing reaches the default branch without passing it), "Require it, admins can still push directly" second and "Not now" third. On yes, run `gauntlet connect github --require-check` yourself, adding `--admin-bypass` for the second choice: it creates the ruleset with the GitHub CLI. Only if it fails (no `gh`, not signed in, no admin rights) tell me the step to do by hand, using what it printed.
